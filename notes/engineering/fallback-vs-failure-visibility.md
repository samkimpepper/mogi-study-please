# 장애 폴백과 실패 가시성의 트레이드오프

> [!summary]
> 좋은 폴백은 제한사항을 드러내면서 핵심 기능을 축소해 제공한다. 실패를 성공처럼 보이게 하거나 낡은 데이터를 최신 데이터처럼 보여주는 폴백은 장애를 숨기고 사용자 신뢰와 관측성을 함께 잃게 만든다.

## 처음 나온 반론

Supabase 장애 때 `mock_kr` 정적 데이터를 보여주는 런타임 폴백을 제거하자 이런 반론이 가능했다.

> 서버가 죽었을 때 아무것도 못 보는 것보다 낡은 데이터라도 보여주는 편이 사용자 경험에 낫지 않을까?

항상 틀린 주장은 아니다. 다만 폴백이 **무엇을 보장하고, 사용자가 그것을 어떻게 해석하는가**를 확인해야 한다.

---

## 좋은 폴백과 장애 위장은 다르다

폴백은 주 경로가 실패했을 때 사용하는 대체 경로다. 좋은 폴백은 기능이 축소되었거나 데이터가 오래되었다는 사실을 숨기지 않는다.

```text
좋은 폴백
실시간 조회 실패
  ↓
“마지막 갱신: 2시간 전” 표시
  ↓
읽기 전용 캐시 제공
```

반면 문제의 `mock_kr` 폴백은 Supabase 요청이 실패하면 과거 정적 데이터를 정상 화면과 같은 모양으로 보여줬다.

```text
문제의 폴백
Supabase 조회 실패
  ↓
옛 정적 mock 데이터 반환
  ↓
정상 화면 렌더
  ↓
사용자와 운영자 모두 장애를 알아차리기 어려움
```

> [!warning]
> 폴백 데이터라는 표시, 생성 시각, 보장 범위가 없다면 사용자는 그것을 현재의 진짜 데이터로 해석한다.

## 낡은 데이터는 단순히 오래된 데이터가 아닐 수 있다

스키마와 제품 기능은 계속 바뀐다. 옛 mock 데이터가 새 필드를 모르거나 새 관계를 표현하지 못하면 화면은 단순히 과거 상태가 아니라 **구조적으로 틀린 상태**를 보여준다.

이번 사례에서는 팔레트 같은 새 구조가 mock 데이터에 없어 실제로 존재하는 항목이 0건처럼 보일 수 있었다.

- 사용자: 데이터가 정말 없다고 오해한다.
- 개발자: 서버 장애가 없다고 오해한다.
- 운영자: 오류 보고가 없어 문제를 발견하지 못한다.

잠깐의 명시적 실패보다 정상처럼 보이는 거짓 성공이 더 큰 신뢰 손실을 만들 수 있다.

---

## 빈 결과와 실패는 다른 상태다

데이터 화면은 적어도 다음 상태를 구분해야 한다.

| 상태 | 의미 | 사용자 표현 |
| --- | --- | --- |
| loading | 아직 결과를 기다리는 중 | 로딩 표시 |
| success | 요청 성공, 데이터 있음 | 정상 목록 |
| empty | 요청 성공, 데이터 0건 | “아직 없어요” |
| error | 요청 자체가 실패 | 오류 문구와 다시 시도 |
| stale | 과거 데이터임을 알고 표시 | 마지막 갱신 시각과 제한 안내 |

오류를 빈 배열이나 정적 mock으로 바꾸면 `error`가 `empty` 또는 `success`로 위장된다. 화면은 부드럽게 유지되지만 시스템의 실제 상태를 잃어버린다.

## 실패를 보이게 만든 것은 새 장애가 아니다

폴백을 제거한 다음 “데이터를 불러오지 못했어요”라는 제보가 들어와도, 그것만으로 새 코드가 장애를 만들었다고 판단하면 안 된다.

```text
변경 전: 실제 실패 → mock 화면 → 아무도 모름
변경 후: 실제 실패 → 오류 분류 → 서버 보고 → 재시도 UI
```

원래 존재하던 실패가 이제 관측 가능해진 것일 수 있다. 첫 확인 위치는 오류 보고 로그이며, 어떤 단계와 어떤 코드로 실패했는지 확인한 뒤 회귀 여부를 판단한다.

> 보이게 된 실패와 새로 생긴 실패를 구분해야 한다.

## graceful degradation을 선택할 기준

다음 질문에 답할 수 있다면 폴백을 유지할 근거가 생긴다.

- 폴백 데이터가 얼마나 오래되었는지 알 수 있는가?
- 사용자에게 현재 데이터가 아니라는 사실을 명확히 표시하는가?
- 잘못된 정보가 의사결정이나 쓰기 작업으로 이어지지 않는가?
- 현재 스키마와 폴백 데이터가 호환되는가?
- 폴백이 실행돼도 장애가 로그와 지표에 기록되는가?
- 주 경로가 복구되면 자동으로 정상 경로로 돌아오는가?

예를 들어 뉴스 읽기 화면은 마지막 캐시를 시각과 함께 보여줄 수 있다. 반면 재고, 결제 상태, 권한 정보처럼 최신성이 중요한 데이터는 오래된 값을 정상처럼 보여주는 것이 더 위험하다.

## fail-open과 fail-closed

폴백 결정은 보안의 fail-open/fail-closed와도 닮았다.

- fail-open: 주 경로가 실패해도 가능한 동작을 계속 허용한다.
- fail-closed: 확신할 수 없으면 동작을 막고 실패를 드러낸다.

모든 기능을 fail-closed로 만들 필요는 없다. 그러나 잘못된 데이터가 사용자 행동이나 데이터 변경으로 이어지는 경로라면 보수적으로 실패하는 편이 안전하다.

## 이번 프로젝트의 결론

200명 규모의 코어 서비스에서 `mock_kr` 런타임 폴백은 다음 이유로 은퇴했다.

1. Supabase 장애를 정상 화면으로 위장했다.
2. 스키마가 진화할수록 실제 데이터와의 괴리가 커졌다.
3. 사용자와 운영자가 장애를 발견하기 어려웠다.
4. 대신 오류 분류, 서버 보고, inline 재시도를 함께 제공할 준비가 됐다.

삭제한 것은 `mock_kr.json` 파일 자체가 아니라 런타임 대체 경로다. 파일은 import 스크립트 입력으로 계속 사용할 수 있으므로, “데이터 자산 삭제”와 “장애 폴백 제거”도 구분해야 한다.
