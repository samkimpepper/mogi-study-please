# 에러 코드 계약과 하위 호환 배포 순서

> [!summary]
> 에러 코드는 단순한 구현 상세가 아니라 DB·백엔드·프론트가 함께 소비하는 계약이다. 생산자와 소비자가 서로 다른 버전으로 잠시 공존할 수 있으므로, 새 코드를 먼저 이해할 수 있게 만들고 안전한 순서로 배포해야 한다.

## 처음 발견한 문제

사이드 프로젝트에서는 서로 다른 권한 실패가 모두 PostgreSQL `42501`로 전달됐다.

```text
로그인하지 않음
남의 글을 수정함
남의 발색 사진을 근거로 사용함
  ↓
모두 42501
```

프론트는 같은 코드 안에서 정확한 이유를 구분할 수 없어 DB가 보낸 에러 문장 일부를 읽는 message sentinel 파싱에 의존했다.

```ts
if (error.code === '42501' && error.message.includes('author')) {
  // 남의 글 수정으로 추정
}
```

문구는 사람에게 설명하기 위한 값이라 번역, 오탈자 수정, DB 함수 변경으로 쉽게 바뀐다. 프로그램의 분기 기준으로 사용하면 문장 변경이 로직 버그가 된다.

---

## 코드와 메시지의 책임을 나눈다

| 값 | 소비자 | 역할 |
| --- | --- | --- |
| 안정적인 에러 코드 | 프로그램, 로그, 모니터링 | 실패 종류 식별과 분기 |
| 사용자 메시지 | 사람 | 이해하기 쉬운 안내 |
| 원인과 상세 정보 | 개발자와 운영자 | 디버깅과 추적 |

이번 변경에서는 권한 실패의 의미를 전용 코드로 나눴다.

- `P0403`: 남의 글이므로 수정·삭제할 수 없음
- `P0405`: 남의 발색 사진을 근거로 사용할 수 없음
- 기존 인증 관련 실패: 별도의 기존 의미로 분류

```text
PostgreSQL 함수
  ↓ P0403 또는 P0405
classifyDataError
  ↓ 애플리케이션 에러
사용자에게 상황에 맞는 문구 표시
```

가드 조건 자체를 바꾼 것이 아니라 **거부 이유를 전달하는 코드만 더 정확하게 만든 것**이다. 차단 뒤 행이 그대로 유지되는 검증으로 데이터 동작이 달라지지 않았음도 확인했다.

## 에러 코드도 API 계약이다

프론트는 DB가 어떤 코드를 보내는지 알아야 올바른 메시지를 고를 수 있다. 즉 에러 코드는 HTTP 응답 DTO의 필드나 이벤트 메시지 스키마처럼 생산자와 소비자 사이의 계약이다.

```text
생산자: PostgreSQL 함수 또는 백엔드
계약: P0403, P0405의 의미
소비자: classifyDataError와 UI
```

코드를 추가하거나 의미를 바꾸면 생산자와 소비자의 배포 버전이 잠시 어긋날 수 있다는 점까지 고려해야 한다.

---

## 왜 DB를 프론트보다 먼저 배포했는가

새 프론트는 `P0403`과 `P0405`를 기준으로 사용자 문구를 고른다. 그런데 프론트를 먼저 배포하고 DB가 여전히 모든 경우에 `42501`을 반환하면 새 소비자가 기대한 계약을 옛 생산자가 제공하지 못한다.

```text
새 프론트 먼저 배포
  ↓
프론트는 P0403/P0405를 기대
  ↓
옛 DB는 42501 반환
  ↓
로그인 사용자의 소유권 실패를 “로그인 필요”로 잘못 안내
```

그래서 이번 변경은 다음 순서를 지켰다.

```text
1. DB migration 배포: P0403/P0405를 생산할 수 있게 함
2. 원격 DB 함수와 migration 상태 확인
3. 새 에러 코드를 소비하는 프론트 배포
```

새 DB가 먼저 배포된 짧은 구간에 구버전 프론트가 어떤 반응을 보이는지도 확인해야 한다. 구버전 프론트가 모르는 코드를 일반 오류로 안전하게 처리한다면 DB 우선 배포가 가능하다. 그렇지 않다면 소비자에게 새 코드를 먼저 인식시키되 사용하지 않게 하는 호환 단계가 필요하다.

## 호환성 표로 배포 순서를 확인한다

| 생산자 | 소비자 | 예상 결과 |
| --- | --- | --- |
| 옛 DB: `42501` | 옛 프론트 | 기존 동작 |
| 새 DB: `P0403/P0405` | 옛 프론트 | 안전한 일반 오류로 처리되는지 확인 필요 |
| 옛 DB: `42501` | 새 프론트 | 잘못된 사용자 문구가 나올 수 있음 |
| 새 DB: `P0403/P0405` | 새 프론트 | 목표 동작 |

배포 순서는 “항상 DB 먼저”처럼 외우기보다, 이 네 조합 중 실제 배포 중 나타날 조합이 안전한지를 보고 정한다.

## 더 큰 변경에서는 expand-and-contract를 사용한다

한 번에 계약을 교체하기 어렵다면 신구 버전이 공존하는 단계를 만든다.

```text
Expand
1. 소비자가 옛 코드와 새 코드를 모두 이해하게 배포
2. 생산자가 새 코드를 보내기 시작

Contract
3. 옛 코드 사용이 사라졌는지 관측
4. 옛 코드 처리와 임시 호환 로직 제거
```

DB 컬럼 이름 변경, 이벤트 스키마 변경, API 응답 필드 변경에도 같은 전략을 사용할 수 있다.

## 코드 변경만으로 완료된 것이 아니다

로컬 migration과 프론트 코드가 맞아도 원격 DB가 적용되지 않았다면 계약은 아직 어긋난 상태다. 이번 작업은 다음 증거로 원격 반영까지 확인했다.

- migration 목록에서 대상 버전의 local과 remote 일치
- 원격 함수 본문에서 `P0403`, `P0405` 확인
- 과거 `42501` author sentinel이 남아 있지 않음을 확인
- 권한 차단 후 대상 행이 유지되는 검증 통과

> 배포 완료는 코드를 푸시한 시점이 아니라, 실제 생산자가 새 계약을 제공하고 소비자가 그것을 올바르게 해석하는지 확인한 시점이다.

## Spring 백엔드에서 연결하면

Spring API에서도 같은 문제가 생긴다.

- `ErrorCode` enum의 이름이나 의미 변경
- HTTP status 변경
- 응답 DTO의 `code` 필드 변경
- Kafka 이벤트의 오류 타입 변경
- DB 저장 프로시저가 반환하는 SQLSTATE 변경

프론트나 다른 서비스가 이 값을 분기 기준으로 사용한다면 내부 리팩터링이 아니라 계약 변경으로 다뤄야 한다.
