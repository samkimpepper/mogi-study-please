# Go Green Tea GC와 페이지 단위 tracing

## 한 줄 정리

Green Tea GC는 객체의 생존 여부를 페이지 단위로 대충 판단하는 기술이 아니다. **살아 있는지는 여전히 객체마다 판단하되, 살아 있는 객체를 찾아다니는 작업을 페이지별로 모아서 CPU가 좋아하는 연속적인 메모리 접근으로 바꾸는 최적화**다.

## 공부하게 된 계기

한 시니어 개발자가 다음과 같은 취지의 글을 썼다.

> GC를 object 단위로 수행하지 않고 page 단위로 한다. 페이지별로 seen/scanned 비트맵을 유지한다. 순회를 LIFO(DFS)로 하지 않고 FIFO로 한다. 이미 본 페이지를 또 보는 경우를 줄인다. 결과적으로 순회를 캐시 친화적으로 한다.

내용상 Go의 **Green Tea Garbage Collector**를 설명한 것으로 보인다.

- 공식 설명: [The Green Tea Garbage Collector](https://go.dev/blog/greenteagc)

---

## 먼저 바로잡을 오해

“페이지 단위로 GC한다”는 말을 다음처럼 이해하면 안 된다.

```text
페이지에 살아 있는 객체가 하나라도 있음
→ 페이지 전체를 살림

페이지에 살아 있는 객체가 없음
→ 페이지 전체를 버림
```

Green Tea도 어떤 객체가 살아 있고 죽었는지를 객체별로 추적한다.

달라진 것은 **생존 판정의 단위**가 아니라 **mark 단계에서 처리할 일을 묶는 단위**다.

```text
기존 방식
→ 처리할 객체를 작업 목록에 넣음

Green Tea
→ 처리할 객체가 속한 페이지를 작업 목록에 넣음
→ 페이지 안에서는 객체별 bitmap으로 상태 관리
```

## GC의 mark-sweep 복습

Tracing GC는 객체와 포인터를 그래프로 생각한다.

```text
root
 └→ 객체 A
      ├→ 객체 B
      │    └→ 객체 D
      └→ 객체 C
```

root는 현재 실행 중인 함수의 지역 변수나 전역 변수처럼 확실히 살아 있다고 판단할 수 있는 시작점이다.

### Mark

root에서 포인터를 따라가며 도달 가능한 객체를 살아 있다고 표시한다.

```text
root에서 A 발견
→ A가 가리키는 B와 C 발견
→ B가 가리키는 D 발견
→ A, B, C, D는 살아 있음
```

### Sweep

mark 단계에서 한 번도 도달하지 못한 객체의 메모리를 재사용 가능하게 만든다.

```text
도달함
→ 살아 있는 객체

도달하지 못함
→ 프로그램에서 더 이상 사용할 수 없는 객체
→ 메모리 회수
```

이 글의 핵심은 sweep보다 **mark 단계에서 살아 있는 객체 그래프를 어떻게 효율적으로 순회하는가**에 있다.

## 기존 객체 단위 순회의 문제

기존의 일반적인 graph flood는 발견한 객체를 작업 목록에 넣는다.

```text
객체 A 발견
→ A를 작업 목록에 넣음
→ A를 꺼내 내부 포인터 확인
→ B와 C 발견
→ B와 C를 작업 목록에 넣음
→ 다음 객체를 꺼내 계속 순회
```

논리적으로 연결된 객체가 물리 메모리에서도 가깝다는 보장은 없다.

```text
객체 A: 메모리의 앞부분
객체 B: 메모리의 먼 뒷부분
객체 C: 다시 중간 부분
객체 D: 또 다른 먼 부분
```

포인터 관계만 따라가면 실제 메모리 접근은 다음처럼 될 수 있다.

```text
A 읽기
→ 멀리 있는 B 읽기
→ 멀리 있는 D 읽기
→ 다시 멀리 있는 C 읽기
```

CPU 입장에서는 작은 작업을 하면서 메모리 여기저기로 계속 뛰어다니는 형태다.

- 다음에 읽을 위치를 예측하기 어렵다.
- 필요한 데이터가 CPU cache에 없을 가능성이 크다.
- 메인 메모리에서 데이터가 도착하기를 기다리는 시간이 늘어난다.
- 작고 불규칙한 작업이라 CPU의 prefetch와 vector 연산을 활용하기 어렵다.

> 객체 그래프에서 가깝다는 것과 물리 메모리에서 가깝다는 것은 서로 다른 이야기다.

## Green Tea는 페이지를 작업 단위로 삼는다

여러 객체는 연속된 메모리 덩어리인 페이지에 배치된다.

Go Green Tea 설명에서 페이지는 8KiB 크기의 Go heap 관리 단위이며, 한 페이지에는 같은 크기의 객체가 들어간다. 여기서 말하는 페이지는 운영체제의 hardware page와 반드시 같은 개념은 아니다.

```text
페이지 A

[객체 A1][객체 A2][객체 A3][빈 slot][객체 A4]
```

기존 방식의 작업 목록에는 객체가 들어간다.

```text
객체 작업 목록

[A1, B3, C2, A2, B1 ...]
```

Green Tea의 작업 목록에는 페이지가 들어간다.

```text
페이지 작업 목록

[페이지 A, 페이지 B, 페이지 C ...]
```

페이지 A의 차례가 되면 그 페이지에서 새로 발견된 객체들을 모아서 처리한다.

```text
페이지 A 차례

A1 scan
A2 scan
A4 scan
```

서로 가까운 메모리를 연속으로 읽을 가능성이 커지기 때문에 CPU cache를 활용하기 좋아진다.

## `seen`과 `scanned` bitmap

작업 목록에 페이지를 넣더라도 그 페이지에서 어느 객체를 처리해야 하는지는 알아야 한다. Green Tea는 페이지마다 객체별 상태를 나타내는 두 bitmap을 관리한다.

### `seen`

이 객체를 가리키는 포인터를 발견했는지 나타낸다.

```text
seen = 1
→ root 또는 다른 객체를 통해 도달함
→ 살아 있는 객체로 발견됨
```

### `scanned`

이 객체 내부의 포인터까지 이미 확인했는지 나타낸다.

```text
scanned = 1
→ 이 객체가 가리키는 다음 객체들까지 조사 완료
```

객체를 살아 있다고 **발견하는 것**과 그 객체 내부를 **조사하는 것**은 서로 다른 단계이므로 두 상태가 필요하다.

| `seen` | `scanned` | 의미 |
| ---: | ---: | --- |
| 0 | 0 | 아직 발견하지 못한 객체 |
| 1 | 0 | 살아 있다고 발견했지만 내부 포인터는 아직 조사하지 않음 |
| 1 | 1 | 발견했고 내부 포인터 조사까지 완료 |

예를 들어 페이지 A에 객체가 다섯 개 있다고 해보자.

```text
객체 위치:  A1 A2 A3 A4 A5

seen:       1  1  0  1  0
scanned:    1  0  0  0  0
```

이번에 scan해야 할 객체는 `seen = 1`이면서 `scanned = 0`인 A2와 A4다.

```text
처리 대상 = seen AND NOT scanned
```

bitmap을 비교하면 이미 처리한 A1을 다시 조사하지 않고 새로 발견된 객체만 빠르게 고를 수 있다.

---

## LIFO와 DFS

기존 Go GC의 객체 작업 목록은 대략 LIFO, 즉 stack처럼 동작한다.

```text
마지막에 넣은 객체를 먼저 꺼냄
→ 한 갈래를 깊게 따라감
→ DFS와 비슷한 순회
```

```text
A에서 B 발견
→ 바로 B 쪽으로 이동
→ B에서 C 발견
→ 바로 C 쪽으로 이동
```

객체의 포인터를 발견하자마자 따라가면 페이지 A, B, C 사이를 계속 오갈 수 있다.

```text
페이지 A
→ 페이지 B
→ 페이지 C
→ 다시 페이지 A
```

---

## FIFO를 사용하는 진짜 이유

Green Tea는 페이지 작업 목록을 FIFO, 즉 queue처럼 사용한다.

```text
먼저 들어온 페이지를 먼저 처리
```

이 선택의 핵심은 BFS 자체가 DFS보다 우월해서가 아니다. **페이지가 queue에서 차례를 기다리는 동안 같은 페이지의 처리 대상 객체가 더 모이게 하기 위해서**다.

```text
페이지 A를 queue에 넣음
→ 현재 A1이 seen 상태

페이지 A가 기다리는 동안
→ 다른 포인터를 통해 A2 발견
→ 또 다른 포인터를 통해 A4 발견

페이지 A 차례
→ A1, A2, A4를 한꺼번에 scan
```

발견한 객체를 곧바로 하나씩 처리하기보다, 같은 페이지의 일을 잠시 모았다가 한 번에 처리하는 전략이다.

> 때로는 바로 일하지 않고 잠깐 기다리는 것이 더 효율적이다. 기다리는 동안 같은 장소에서 할 일이 모이기 때문이다.

---

## 페이지를 정말 한 번만 보는가

그렇지는 않다.

페이지 A를 이미 처리했더라도 나중에 A 안의 새로운 객체가 발견되면 페이지 A가 작업 목록에 다시 들어갈 수 있다.

```text
페이지 A 첫 방문
→ A1, A2 처리
→ scanned 기록

나중에 A3 발견
→ 페이지 A 재방문
→ A1, A2는 이미 scanned
→ A3만 처리
```

따라서 “이미 본 페이지를 절대로 다시 보지 않는다”는 뜻은 아니다.

중복 작업을 줄이는 핵심은 다음 두 가지다.

1. 페이지가 이미 queue에 있다면 페이지를 계속 중복 등록하기보다 해당 객체의 `seen` 비트만 추가한다.
2. 페이지를 다시 방문하더라도 `seen`과 `scanned`의 차이를 이용해 새로 발견된 객체만 처리한다.

결과적으로 같은 페이지를 불필요하게 자주 오가거나, 이미 처리한 객체를 다시 조사하는 일을 줄인다.

---

## 왜 cache 친화적인가

CPU는 요청한 데이터 주변을 cache line 단위로 함께 가져온다.

페이지 A의 A1을 읽으면 근처의 A2와 A3도 cache에 들어올 가능성이 높다.

```text
A1 읽음
→ 주변의 A2와 A3도 cache에 들어옴
→ 바로 A2와 A3 처리
→ cache hit 가능성 증가
```

반대로 포인터를 따라 먼 메모리를 계속 오가면 앞서 읽은 데이터가 다시 필요할 때 cache에서 이미 밀려났을 수 있다.

```text
A1
→ 멀리 있는 B7
→ 멀리 있는 C2
→ 다시 A3
```

두 방식을 비교하면 다음과 같다.

```text
객체 단위 LIFO
→ 포인터 관계를 따라 메모리를 불규칙하게 이동
→ 여러 위치에서 작은 작업을 수행
→ cache miss와 메모리 대기 증가
```

```text
페이지 단위 FIFO
→ 같은 페이지에서 발견된 객체를 모음
→ 가까운 메모리를 연속해서 처리
→ cache, prefetch, vector 연산 활용 가능
```

페이지별 metadata도 한곳에 모여 있으므로 cache에 올려두기 쉽다. 객체 대신 페이지를 작업 목록에 넣기 때문에 작업 목록 자체도 더 작아지고, 여러 GC worker가 공유하는 작업 목록의 경쟁도 줄일 수 있다.

## 창고 선반 비유

기존 객체 단위 GC는 물건에 적힌 다음 물건의 위치를 발견하는 즉시 따라가는 직원과 비슷하다.

```text
A 선반의 물건 확인
→ B 선반으로 이동
→ D 선반으로 이동
→ 다시 A 선반으로 이동
```

Green Tea는 확인할 물건이 있는 선반 자체를 작업 대기열에 등록한다.

```text
A 선반에서 확인할 물건 발견
→ A 선반을 대기열에 등록

A 선반이 기다리는 동안
→ A 선반의 다른 물건도 확인 대상으로 발견
→ 물건에 표시만 추가

A 선반 차례
→ 표시된 물건들을 한꺼번에 확인
```

비유를 대응시키면 다음과 같다.

| GC 개념 | 창고 비유 |
| --- | --- |
| 페이지 | 선반 |
| 객체 | 선반에 있는 물건 |
| `seen` 비트 | 확인 대상으로 발견했다는 표시 |
| `scanned` 비트 | 내용물까지 조사 완료했다는 표시 |
| FIFO queue | 선반 작업 대기열 |

---

## 항상 더 빠른 것은 아니다

Green Tea는 같은 페이지에서 처리할 객체가 여러 개 모일 때 효과가 크다.

객체 그래프가 불규칙해서 매번 페이지당 객체 하나만 발견된다면 다음과 같을 수 있다.

```text
페이지 A에서 객체 1개
페이지 B에서 객체 1개
페이지 C에서 객체 1개
다시 페이지 A에서 객체 1개
```

이 경우 페이지 단위로 작업을 모으기 위한 관리 비용은 추가됐는데, 같은 페이지의 여러 객체를 한꺼번에 처리하는 이득은 얻지 못한다.

Go 공식 설명에서도 workload에 따라 이득이 적거나 없고, 일부는 불리할 수도 있다고 설명한다. 따라서 “페이지 단위이므로 무조건 빠르다”가 아니라 **같은 페이지에서 충분한 작업을 모을 수 있는 workload에서 locality의 이득이 크다**고 이해해야 한다.

---

## 트윗을 평범한 말로 번역하면

> 기존 GC는 살아 있는 객체의 포인터를 발견하는 대로 따라가서 메모리 여기저기를 뛰어다녔다. Green Tea는 처리할 객체를 페이지별 bitmap에 표시하고 페이지를 FIFO queue에 잠시 둬서 같은 페이지의 작업이 모이게 한다. 페이지 차례가 되면 아직 scan하지 않은 객체들을 연속으로 처리한다. 그 결과 중복 작업과 불규칙한 메모리 이동을 줄이고 CPU cache와 vector 연산을 더 잘 활용할 수 있다.

> [!summary]
> 쓰레기를 찾는 기준을 객체에서 페이지로 바꾼 것이 아니다. 살아 있는 객체를 찾아다니는 작업을 페이지별로 묶어 CPU가 좋아하는 연속 작업으로 바꾼 것이다.
