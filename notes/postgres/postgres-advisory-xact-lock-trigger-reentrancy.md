# pg_advisory_xact_lock과 trigger가 같은 키를 쓰는 이유

## 🎯 왜 공부했나

사이드프로젝트에서 다음 설명을 읽었다.

> 동시 replace 직렬화 = shade 단위 `pg_advisory_xact_lock` (CR-01, trigger와 같은 키) — 실측 = `supabase/tests/shade_color_families_concurrency_verify.sh`

처음에는 다음 부분들이 한꺼번에 섞여 있어서 이해하기 어려웠다.

- `pg_advisory_xact_lock`이 정확히 무엇인지
- replace 함수가 잠금을 잡는데 트리거가 왜 또 잠금을 잡는지
- 함수와 트리거가 왜 같은 잠금 키를 사용해야 하는지
- 함수가 이미 잡은 잠금을 트리거가 다시 요청하면 자기 자신을 기다리게 되지 않는지

이 문장을 먼저 일상어로 번역하면 다음과 같다.

> 같은 shade의 색군을 교체하는 요청 두 개가 동시에 들어와도 작업이 서로 섞이지 않도록 한 줄로 세운다. 그 줄을 세우는 도구가 shade 단위의 `pg_advisory_xact_lock`이다. 기존 트리거도 같은 데이터를 보호하고 있으므로, 함수와 트리거가 동일한 잠금 번호를 사용한다. 실제로 동시에 실행했을 때 줄을 서는지는 별도의 동시성 검증 스크립트로 확인했다.

---

## 🧩 먼저 세 가지 역할을 분리하기

이 내용을 이해하려면 replace 함수, 트리거, advisory lock을 서로 다른 역할로 분리해서 봐야 한다.

### 1. 함수는 색군 전체를 교체한다

예를 들어 shade 7의 색군을 `[웜톤]`에서 `[쿨톤, 뮤트]`로 교체한다고 하자.

replace 함수는 대략 다음 순서로 움직인다.

```text
잠금 획득
→ 기존 색군 전부 DELETE
→ 새로운 색군 INSERT
→ COMMIT
```

여기서 중요한 것은 `DELETE`와 `INSERT`가 따로 떨어진 작업이 아니라 **하나의 교체 작업**이라는 점이다.

원하는 의미는 단순히 새 행을 추가하는 것이 아니다.

> "이 shade에 전에 들어 있던 색군 묶음은 모두 버리고, 지금 전달한 새 묶음으로 완전히 교체한다."

따라서 동시 요청을 막을 때도 `INSERT` 한 순간만 보호해서는 부족하다. `DELETE`가 시작되는 함수 진입부부터 새 값의 `INSERT`가 끝날 때까지 전체 흐름을 한 덩어리로 보호해야 한다.

### 2. 트리거는 INSERT 순간에 규칙을 검사한다

트리거는 별도의 프로그램이나 별도의 트랜잭션이 아니다.

> 트리거는 테이블에 `INSERT`, `UPDATE`, `DELETE` 같은 사건이 일어났을 때, 그 작업을 수행하는 **같은 트랜잭션 안에서 자동 실행되는 DB 코드**다.

색군 테이블의 트리거는 `INSERT`가 들어올 때 대략 다음처럼 움직인다.

```text
INSERT 시도
→ 트리거 자동 실행
→ 현재 shade의 색군 개수 확인
→ 2개를 초과하면 거부
→ 괜찮으면 INSERT 진행
```

이 트리거의 주요 임무는 다음 불변식을 지키는 것이다.

> shade 하나에는 color family를 최대 2개까지만 연결할 수 있다.

관련된 `COUNT(*)` 트리거의 기본 동시성 문제는 [[postgres-locks-count-trigger-concurrency]]에서 별도로 정리했다.

### 3. Advisory lock은 같은 shade의 작업을 한 줄로 세운다

`pg_advisory_xact_lock`은 실제 테이블이나 행을 자동으로 찾아 잠그는 기능이 아니다. 개발자가 숫자 키에 의미를 부여하고, 같은 키를 사용하는 코드끼리 협력해서 줄을 서는 잠금이다.

예를 들어 의미상 다음과 같은 잠금 번호가 있다고 생각할 수 있다.

```text
K7 = "shade 7의 color family 묶음을 작업 중"
K8 = "shade 8의 color family 묶음을 작업 중"
```

그러면 동작은 다음과 같다.

- shade 7 작업끼리는 모두 `K7`을 요청하므로 한 줄로 선다.
- shade 8 작업은 `K8`을 사용하므로 shade 7 작업과 동시에 진행할 수 있다.
- DB는 `K7`이 shade 7을 뜻한다는 사실을 모른다. 그 의미는 개발자들이 코드로 맺은 약속이다.

## 🔍 pg_advisory_xact_lock 이름 해부하기

`pg_advisory_xact_lock`을 단어별로 나누면 역할이 조금 더 선명해진다.

### pg

PostgreSQL이 제공하는 내장 함수라는 뜻으로 이해하면 된다.

### advisory

DB가 데이터의 의미를 알아서 판단해 거는 잠금이 아니라, 개발자가 잠금 키의 의미와 사용 규칙을 정하는 **약속형 잠금**이다.

`SELECT ... FOR UPDATE`는 실제 행을 잠근다.

```sql
SELECT *
FROM shades
WHERE id = 7
FOR UPDATE;
```

Postgres는 이 잠금이 `shades.id = 7` 행에 걸렸다는 사실을 안다.

반면 advisory lock은 숫자 키를 잠근다.

```sql
SELECT pg_advisory_xact_lock(123456789);
```

Postgres는 `123456789`가 shade인지, 주문인지, 사용자인지 알지 못한다.

> "이 숫자는 shade 7의 색군 작업을 뜻한다"고 개발자가 약속하고, 관련된 모든 코드가 같은 숫자를 사용할 때만 잠금이 제대로 작동한다.

### xact

`transaction`의 줄임말이다.

이 잠금은 트랜잭션 범위에서 유지된다.

```text
트랜잭션 시작
→ 잠금 획득
→ DELETE
→ INSERT
→ COMMIT 또는 ROLLBACK
→ 잠금 자동 해제
```

성공해서 `COMMIT`해도 풀리고, 오류가 생겨 `ROLLBACK`해도 풀린다. 별도의 unlock 코드를 호출하지 않아도 되므로 잠금 해제를 깜빡하는 위험을 줄일 수 있다.

### lock

같은 잠금 키를 다른 트랜잭션이 이미 가지고 있다면, 먼저 잡은 트랜잭션이 끝날 때까지 기다리게 한다.

## 🏷️ 문자열 이름표가 실제 잠금 키가 되는 과정

코드에서는 다음처럼 문자열을 만든 뒤 해시해서 숫자로 바꾼다.

```sql
PERFORM pg_advisory_xact_lock(
  hashtextextended('shade_color_families:' || p_shade_id::text, 0)
);
```

예를 들어 `p_shade_id`가 `174`라면 사람이 이해하는 논리적인 이름표는 다음과 같다.

```text
shade_color_families:174
```

`hashtextextended`는 이 문자열을 고정된 큰 숫자로 변환하고, `pg_advisory_xact_lock`은 그 숫자를 잠금 키로 사용한다.

```text
shade_color_families:174
→ hashtextextended(...)
→ 숫자 잠금 키
→ 같은 숫자를 요청하는 다른 트랜잭션은 대기
```

정확히 말하면 advisory lock이 문자열 이름표를 직접 받는 것은 아니다. 개발자가 읽기 쉬운 문자열을 먼저 만들고, 그 문자열을 숫자로 변환해 잠금 키로 사용하는 것이다.

shade ID가 잠금 이름에 포함되므로 잠금 범위도 shade별로 나뉜다.

```text
shade_color_families:7 → K7
shade_color_families:8 → K8
```

모든 shade의 저장을 하나의 전역 잠금으로 막는 것이 아니다. **같은 shade를 수정하는 작업끼리만** 기다리게 한다.

## 🚪 색군 테이블로 들어가는 문은 두 개다

색군 테이블을 수정하는 경로를 두 개의 문이라고 생각할 수 있다.

```text
앱의 RPC replace 함수 ───────────┐
                                 ├─ shade_color_families 테이블
직접 INSERT ─ 트리거 자동 실행 ──┘
```

### 함수 문

앱의 정상적인 저장은 RPC replace 함수를 통한다.

함수는 기존 값을 `DELETE`하고 새 값을 `INSERT`하므로, 함수의 시작부터 전체 교체 작업을 잠가야 한다.

### 직접 INSERT 문

관리자 도구, SQL, 다른 API 또는 아직 허용된 우회 경로를 통해 테이블에 직접 `INSERT`가 들어올 수도 있다.

이 경로는 replace 함수의 코드를 실행하지 않는다. 대신 테이블에 붙어 있는 트리거가 자동으로 실행되어 최대 2개 규칙을 검사한다.

> advisory lock은 같은 키를 사용하는 코드만 줄 세운다. 따라서 함수만 잠금을 사용하고 직접 INSERT 경로가 잠금에 참여하지 않으면, 직접 INSERT는 함수가 작업 중이어도 들어올 수 있다.

트리거도 잠금을 잡는 이유가 바로 여기에 있다. 직접 INSERT 경로까지 같은 줄에 참여시키는 것이다.

## 🔑 함수와 트리거가 같은 키를 써야 하는 이유

함수와 트리거는 서로 다른 위치에 있는 코드지만, 실제로 보호하려는 대상은 같다.

```text
보호 대상 = "shade N의 color family 묶음"
```

따라서 두 코드가 사용하는 잠금 키도 같아야 한다.

```sql
-- replace 함수
pg_advisory_xact_lock(
  hashtextextended('shade_color_families:' || p_shade_id::text, 0)
)

-- INSERT 트리거
pg_advisory_xact_lock(
  hashtextextended('shade_color_families:' || NEW.shade_id::text, 0)
)
```

변수 이름은 `p_shade_id`와 `NEW.shade_id`로 다르지만, 두 값이 모두 shade 7이라면 최종 문자열은 똑같다.

```text
shade_color_families:7
```

따라서 해시한 숫자도 같고, 같은 잠금 앞에서 한 줄로 서게 된다.

### 같은 키일 때

함수가 먼저 shade 7 잠금을 잡았다고 하자.

```text
함수 트랜잭션 A: K7 획득 ─ DELETE ─ INSERT ─ COMMIT
직접 INSERT B:    K7 요청 ─────── 대기 ─────── 획득 후 개수 검사
```

직접 INSERT의 트리거는 `K7`을 요청하다가 기다린다. A의 교체 작업이 끝난 다음 최종 상태를 기준으로 개수를 검사할 수 있다.

반대로 직접 INSERT 트랜잭션이 먼저 `K7`을 잡고 있다면 replace 함수가 시작 지점에서 기다린다.

### 다른 키라면

잠금 키는 DB가 자동으로 만들어 주는 것이 아니다. 개발자가 코드에 직접 적는다.

함수 코드를 작성하면서 다음처럼 다른 문자열을 적을 수도 있었다.

```sql
-- 트리거가 사용하는 실제 논리적 이름
'shade_color_families:' || shade_id

-- 함수 이름을 보고 잘못 따로 만들 수도 있었던 이름
'set_shade_color_families:' || shade_id
```

두 문자열은 비슷해 보여도 해시 결과는 완전히 다른 숫자가 된다.

```text
함수:   K_replace_7 잠금
트리거: K_count_7 잠금
```

Postgres 입장에서는 서로 아무 관계도 없는 잠금 두 개다. 함수와 트리거가 각각 자기 잠금을 성공적으로 얻고 동시에 진행할 수 있다.

```text
함수 A:       K_replace_7 획득 → 작업 진행
직접 INSERT B: K_count_7 획득  → 기다리지 않고 작업 진행
```

함수는 자기 줄, 트리거는 자기 줄에 서기 때문에 한쪽 작업이 끝나기를 기다리지 않는다. 그러면 같은 shade의 색군 묶음을 동시에 만지면서도 서로의 작업을 무시하게 된다.

> "trigger와 같은 키"라는 주석은 단순한 구현 설명이 아니다. 보호 대상이 같은 코드이므로 잠금 규약도 공유해야 하며, 나중에 둘 중 한쪽의 문자열만 바꾸면 안 된다는 경고이기도 하다.

화장실 한 칸에 문이 두 개 있다고 생각하면 된다.

> 두 문에 서로 다른 "사용 중" 팻말을 달면, 양쪽 사람이 각자 빈 화장실이라고 생각하고 동시에 들어온다. 문이 두 개여도 "사용 중" 팻말은 하나를 공유해야 한다.

## ⏰ 트리거 잠금만으로 부족하고 함수 시작에서도 잠가야 하는 이유

트리거는 `INSERT` 사건이 발생해야 실행된다. replace 함수의 앞부분인 `DELETE` 단계에서는 아직 트리거가 등장하지 않는다.

```text
DELETE ← INSERT 트리거가 아직 실행되지 않음
INSERT ← 여기서 트리거 실행
```

함수 두 개가 동시에 실행되면 트리거가 잠금을 잡기 전부터 두 교체 작업이 섞일 수 있다.

기존 색군이 `[빨강]`인 상황에서 다음 두 요청이 동시에 들어왔다고 하자.

```text
함수 A: 기존 값을 지우고 [파랑]으로 교체하려 함
함수 B: 기존 값을 지우고 [초록]으로 교체하려 함
```

함수 시작에 잠금이 없다면 둘 다 `DELETE` 단계에 진입할 수 있다.

```text
A: DELETE 시작 ───────────── INSERT [파랑]
B:      DELETE 시작 ───────────── INSERT [초록]
```

Postgres의 행 잠금과 MVCC 때문에 실제 세부 대기 순서는 달라질 수 있지만, 중요한 문제는 B의 "전체 교체"가 A의 최종 결과를 본 뒤 처음부터 실행되는 것이 아니라는 점이다. 두 함수의 `DELETE → INSERT` 묶음이 순서대로 직렬화되지 않는다.

그 결과 다음과 같은 문제가 생길 수 있다.

- 마지막 요청의 값으로 완전히 교체되어야 하는데 두 요청의 값이 섞인다.
- 최대 2개 검사에 걸려 한 요청이 예상하지 못하게 실패한다.
- 검사 우회 경로가 있다면 최대 개수 불변식까지 깨질 수 있다.

트리거가 잠금을 잡는 시점은 이미 `DELETE` 이후이므로 이 문제를 완전히 막을 수 없다.

그래서 replace 함수는 첫 단계에서 잠금을 잡는다.

```text
A: K7 잠금 → DELETE → INSERT → COMMIT
B: K7 요청 ───── 기다림 ─────→ 잠금 → DELETE → INSERT → COMMIT
```

이제 B는 `DELETE`조차 시작하지 못하고 기다린다. A가 커밋한 최종 상태를 본 다음 B의 완전한 교체 작업이 시작된다.

두 잠금 위치의 목적을 구분하면 다음과 같다.

| 잠금 위치 | 보호하는 범위 | 필요한 이유 |
| --- | --- | --- |
| replace 함수 진입부 | `DELETE → INSERT` 전체 | 동시 replace 작업이 서로 섞이지 않게 함 |
| INSERT 트리거 | 직접 INSERT의 개수 검사 | 함수를 우회한 INSERT도 같은 잠금 규약에 참여시킴 |

## 💡 가장 헷갈렸던 부분: 함수와 트리거가 같은 잠금을 잡으면 어떻게 되나

처음에는 다음과 같은 의문이 생겼다.

> 함수가 이미 `K7` 잠금을 잡았는데, 그 함수가 `INSERT`해서 실행된 트리거도 `K7`을 요청하면 트리거가 함수의 잠금이 풀릴 때까지 기다리는 것 아닐까? 그러면 함수가 자기 자신 때문에 영원히 멈추지 않을까?

그렇지 않다.

여기서 가장 중요한 사실은 **트리거가 별도 트랜잭션이 아니라는 것**이다.

함수에서 실행한 `INSERT` 때문에 트리거가 실행되면 함수와 트리거는 같은 트랜잭션에 속한다.

```text
트랜잭션 A
  ├─ replace 함수가 K7 잠금 획득
  ├─ DELETE
  └─ INSERT
       └─ 트리거 자동 실행
            └─ 같은 트랜잭션 A가 K7 잠금 요청
```

트랜잭션 A가 이미 가진 잠금을 같은 트랜잭션 A가 다시 요청하는 것이므로 자기 자신을 기다리지 않는다. 바로 통과한다.

반면 다른 요청에서 시작된 트랜잭션 B는 별개의 트랜잭션이므로 기다려야 한다.

```text
트랜잭션 A: K7 획득 ─ DELETE ─ INSERT ─ COMMIT
트랜잭션 B: K7 요청 ─────── 대기 ─────── 획득 후 실행
```

판단 기준을 표로 정리하면 다음과 같다.

| 잠금 키 | 요청 주체 | 결과 |
| --- | --- | --- |
| 같은 키 | 같은 트랜잭션 | 이미 자신이 가진 잠금이므로 통과 |
| 같은 키 | 다른 트랜잭션 | 먼저 잡은 트랜잭션이 끝날 때까지 대기 |
| 다른 키 | 다른 트랜잭션 | 서로 다른 잠금이므로 동시에 진행 가능 |

따라서 "같은 이름표를 쓰니까 한 줄로 선다"는 설명은 **서로 다른 트랜잭션끼리** 줄을 세우는 이유로 맞다.

하지만 "함수 안에서 실행된 트리거가 왜 자기 자신에게 막히지 않는가"에 답하려면 다음 조건까지 붙여야 한다.

> 함수와 트리거는 같은 advisory lock 키를 사용하지만, 둘 다 **같은 트랜잭션**에서 실행되므로 자기 자신이 획득한 잠금을 기다리지 않는다.

## ☕ Java의 재진입 락과 같은 패턴

이 동작이 익숙하게 느껴졌던 이유는 Java의 재진입 락과 매우 비슷하기 때문이다.

Java의 `synchronized`는 같은 스레드가 이미 획득한 모니터 락에 다시 들어갈 수 있다.

```java
synchronized void replace() {
    validate();
}

synchronized void validate() {
    // 같은 스레드가 같은 모니터 락에 다시 진입할 수 있다.
}
```

만약 같은 스레드가 자기가 잡은 락에 다시 들어갈 수 없다면 `replace()`가 `validate()`를 부르는 순간 자기 자신을 기다리는 문제가 생긴다. 재진입 가능한 락은 이를 허용한다.

이번 PostgreSQL 흐름과 대응하면 다음과 같다.

| Java | PostgreSQL |
| --- | --- |
| 같은 스레드 | 같은 트랜잭션 |
| 같은 객체의 모니터 락 | 같은 advisory lock 키 |
| 다른 스레드는 대기 | 다른 트랜잭션은 대기 |
| 같은 스레드는 재진입 | 같은 트랜잭션은 이미 가진 잠금을 다시 요청해도 통과 |

전체 호출 구조도 거의 같다.

```text
replace 함수
└─ K7 잠금 획득
   └─ INSERT
      └─ 트리거 실행
         └─ K7 다시 요청 → 같은 트랜잭션이므로 재진입
```

Java의 `ReentrantLock`, `synchronized`에서 본 감각을 PostgreSQL 트랜잭션 잠금에 연결해서 이해할 수 있다.

다만 완전히 같은 API라는 뜻은 아니다. Java에서는 스레드와 JVM 객체를 기준으로 생각하고, 여기서는 PostgreSQL 세션에서 실행 중인 트랜잭션과 숫자 advisory lock 키를 기준으로 생각한다. **자기 실행 흐름이 이미 가진 동일한 잠금에 다시 들어갈 수 있다**는 핵심 성질이 닮았다.

## 🧰 백엔드에서 자주 만나는 같은 계열의 패턴

이번 방식은 시스템 전체를 하나의 락으로 막는 것이 아니다. 비즈니스 자원의 ID를 잠금 키로 사용해 같은 자원을 수정하는 작업끼리만 줄 세운다.

```text
shadeId, orderId, userId, productId
→ 특정 비즈니스 자원을 나타내는 키
→ 같은 키의 작업만 직렬화
```

비슷한 생각은 다음과 같은 곳에서 자주 등장한다.

- Java의 `synchronized`, `ReentrantLock`
- 주문 ID를 키로 사용하는 Redis 분산 락
- `SELECT ... FOR UPDATE`로 동일 주문이나 재고 행 변경을 직렬화하는 방식
- 같은 키의 중복 요청을 하나만 실행하는 single-flight
- 사용자 ID나 상품 ID 단위로 만드는 keyed mutex

공통된 생각은 다음과 같다.

> 시스템 전체를 잠그지 않고, 동일한 비즈니스 자원을 건드리는 작업끼리만 한 줄로 세운다.

이번 사례에서는 shade 하나와 그 shade에 연결된 color family 묶음을 하나의 비즈니스 단위로 본다.

```text
하나의 보호 단위

shade 7
└─ shade 7에 연결된 color family 묶음 전체
```

DDD 용어를 빌리면 shade와 그 색군 묶음을 하나의 aggregate처럼 보고, **aggregate 단위로 직렬화**한다고 이해할 수도 있다.

그래서 이 방식을 다음과 같이 표현할 수 있다.

- 리소스 키 기반 트랜잭션 락
- keyed lock 또는 keyed mutex
- aggregate 단위 직렬화

## 🧠 최종 정리

### 함수는 왜 잠그나

replace 함수의 `DELETE → INSERT` 전체가 하나의 교체 작업이므로, 다른 replace 작업과 섞이지 않도록 함수 시작 지점에서 잠근다.

### 트리거는 왜 잠그나

replace 함수를 거치지 않고 테이블에 직접 `INSERT`하는 경로도 최대 2개 규칙을 지켜야 한다. 트리거가 잠금을 잡으면 직접 INSERT도 같은 동시성 규약에 참여한다.

### 왜 같은 키인가

함수와 트리거가 모두 `shade N의 color family 묶음`이라는 같은 비즈니스 자원을 보호하기 때문이다. 다른 키를 쓰면 서로 다른 줄에 서서 상대 작업을 기다리지 않는다.

### 같은 키를 두 번 요청해도 왜 멈추지 않나

함수의 `INSERT`로 실행된 트리거는 함수와 같은 트랜잭션 안에서 실행된다. 같은 트랜잭션이 자신이 이미 가진 같은 잠금을 다시 요청하는 것이므로 자기 자신을 기다리지 않고 통과한다.

> [!summary]
> 함수는 교체 작업 전체를 잠그고, 트리거는 INSERT 순간의 규칙 검사를 담당한다. 둘은 같은 shade의 색군 묶음을 보호하므로 같은 advisory lock 키를 쓴다. 함수 안에서 실행된 트리거는 같은 트랜잭션이므로 동일한 잠금을 다시 요청해도 자기 자신에게 막히지 않는다.
