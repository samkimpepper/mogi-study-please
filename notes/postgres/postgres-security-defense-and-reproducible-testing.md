# Postgres 권한 이중 방어와 재현 가능한 보안 테스트

> [!summary]
> 보안 설정은 현재 DB가 안전해 보이는지만 확인하면 안 된다. 권한을 여러 층으로 잠그고, DB를 처음부터 재생한 뒤, 차단과 허용을 양쪽에서 검증해야 한다.

## 오늘 실제로 발견한 문제

사이드 프로젝트 코드 리뷰에서 `anon` 역할의 쓰기를 막는 작업을 검증했다. 마이그레이션으로 권한을 회수한 뒤 현재 로컬 DB에서는 테스트가 통과했지만, `db reset`으로 DB를 처음부터 다시 만들자 seed 파일 끝의 `GRANT ALL`이 권한을 되살렸다.

처음 지적된 테이블 권한뿐 아니라 `create_shade_minimal` 함수의 실행 권한도 같은 방식으로 부활하고 있었다. deny 테스트는 있었지만 일부 테이블에는 정상 사용자의 쓰기를 확인하는 allow 테스트가 없었고, 함수의 인자 개수가 바뀌면서 과거 시그니처를 문자열로 지정한 테스트가 실행되지 않는 문제도 있었다.

> 초록불은 검사한 범위 안에서만 초록이다. 중요한 것은 검사 범위 밖에 무엇이 남아 있는지 묻는 습관이다.

---

## 🔐 RLS와 GRANT는 서로 다른 자물쇠다

RLS와 `GRANT`는 모두 권한과 관계 있지만 담당하는 층이 다르다.

| 장치 | 확인하는 것 | 범위 |
| --- | --- | --- |
| RLS 정책 | 이 역할이 어떤 행을 읽고 변경할 수 있는가 | 행 단위 |
| `GRANT` | 이 역할이 테이블이나 함수를 사용할 수 있는가 | 객체 단위 |

RLS만 설정한 상태에서 누군가 실수로 RLS를 비활성화하면 행 단위 보호가 사라질 수 있다. 반면 필요 없는 `GRANT`까지 회수해두면, RLS가 풀려도 객체 접근 권한이라는 두 번째 자물쇠가 남는다.

```sql
REVOKE INSERT, UPDATE, DELETE, TRUNCATE
ON TABLE public.example
FROM anon;
```

특히 `TRUNCATE`는 행을 하나씩 처리하는 명령이 아니므로 RLS가 막아주지 않는다. 따라서 역할에 불필요한 `TRUNCATE` 권한이 있다면 별도로 회수해야 한다.

> [!warning]
> RLS가 켜져 있다는 사실만으로 테이블의 모든 위험한 작업이 보호된다고 생각하면 안 된다. 객체 권한과 RLS가 각각 무엇을 막는지 나누어 확인해야 한다.

## 🔁 현재 상태보다 재생 경로가 진짜다

내 로컬 DB에서 원하는 권한 상태가 보인다고 해서 그 상태가 코드로 재현된다는 뜻은 아니다. DB의 최종 상태는 대략 다음 경로를 거쳐 만들어진다.

```text
마이그레이션 적용 → seed 실행 → 최종 권한과 데이터 상태
```

마이그레이션에서 권한을 회수했더라도 뒤에 실행되는 seed가 다시 권한을 부여하면 최종 DB는 취약한 상태가 된다. 손으로 고친 상태나 현재 한 번 확인한 상태가 아니라, 처음부터 모든 스크립트를 실행했을 때 만들어지는 상태가 진짜 배포 가능한 상태다.

환경과 스키마를 바꾸는 작업에서는 두 질문을 함께 확인해야 한다.

- 지금 존재하는 DB에서 동작하는가?
- 빈 DB에서 마이그레이션과 seed를 다시 실행해도 같은 결과가 나오는가?

이번 `db reset` 검증은 테이블 권한과 함수 권한이 다시 살아나는 버그를 각각 발견했다. reset은 단순 초기화 절차가 아니라 DB 구성의 재현 가능성을 검증하는 통합 테스트 역할을 한 셈이다.

## 🚦 보안 테스트는 deny와 allow를 짝으로 쓴다

권한 정책에는 항상 두 방향의 요구사항이 있다.

| 방향 | 검증할 질문 | 실패했을 때 드러나는 문제 |
| --- | --- | --- |
| deny | 권한 없는 사용자가 차단되는가? | 정책이 너무 느슨함 |
| allow | 정상 사용자가 허용되는가? | 정책이 너무 강함 |

세션 없는 사용자의 `INSERT`가 차단되는지만 검사하면 모든 쓰기를 막아버린 잘못된 정책도 테스트를 통과한다. 테스트 결과는 초록색이지만 정상 사용자는 북마크, 코어, 컬렉션을 만들지 못할 수 있다.

따라서 같은 기능의 보안 테스트는 다음처럼 한 쌍으로 설계한다.

```text
권한 없는 anon INSERT → 실패해야 성공
인증된 정상 사용자 INSERT → 성공해야 성공
```

이 원칙은 DB 권한뿐 아니라 API 인가 테스트에도 그대로 적용된다. 접근하면 안 되는 사용자의 `403`과 접근해야 하는 사용자의 정상 응답을 모두 확인해야 정책의 경계를 검증할 수 있다.

## 🧩 스키마를 문자열로 아는 테스트도 함께 낡는다

테스트가 함수를 인자 10개짜리 시그니처로 정확히 지정하고 있었는데 실제 함수가 9개 인자로 바뀌면, 테스트는 보안 실패를 발견하기도 전에 대상을 찾지 못한다.

스키마를 바꿀 때는 그 스키마를 직접 호출하는 코드뿐 아니라 다음 소비자도 함께 찾아야 한다.

- 함수 시그니처를 문자열로 지정한 테스트
- 마이그레이션과 seed
- 권한 부여 및 회수 구문
- 문서와 운영 스크립트

그리고 테스트가 CI에 포함돼 실제로 실행되는지도 확인해야 한다. 실행되지 않는 테스트는 오래되어도 아무도 알 수 없으므로 안전망 역할을 하지 못한다.

## 실무 체크 포인트

- RLS 정책과 테이블·함수의 `GRANT`를 별도로 검토한다.
- `anon`, `authenticated`, 서비스 역할의 최종 권한을 각각 확인한다.
- `TRUNCATE`처럼 RLS의 보호 범위 밖에 있는 명령을 확인한다.
- 마이그레이션뿐 아니라 나중에 실행되는 seed의 `GRANT`도 검색한다.
- 권한 변경 후에는 기존 DB 검증과 전체 reset 검증을 함께 수행한다.
- deny 테스트마다 대응하는 allow 테스트가 있는지 확인한다.
- 함수 시그니처 변경 시 테스트, 문서, 권한 SQL을 함께 갱신한다.
- 해당 보안 테스트가 CI에서 실제로 실행되는지 확인한다.

> [!tip] 코드 리뷰에서 물어볼 질문
> “이 테스트가 보장하지 않는 범위는 어디인가?”, “DB를 처음부터 다시 만들면 이 권한이 유지되는가?”, “차단 테스트에 대응하는 정상 허용 테스트도 있는가?”
