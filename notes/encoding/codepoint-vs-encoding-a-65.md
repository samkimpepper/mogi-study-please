# A=65는 어떤 바이트로 저장되는가

> `A = 65`는 "A라는 글자의 유니코드 번호가 65"라는 뜻이지, 항상 디스크에 65라는 바이트 하나로 저장된다는 뜻은 아니다.

---

## 한 줄 정의

**코드포인트**는 글자에 붙은 추상적인 번호이고, **인코딩**은 그 번호를 실제 바이트로 적는 규칙이다.

`A`는 유니코드에서 `U+0041`이고, 10진수로는 `65`다. 여기까지는 "글자 번호표"의 세계다.

그다음 컴퓨터가 파일이나 네트워크에 저장하려면 이 번호를 바이트로 바꿔야 한다. 이때 UTF-8, UTF-16, UTF-32 같은 인코딩 규칙을 고른다.

---

## A는 왜 헷갈리기 쉬운가

`A`는 너무 작은 번호라서 여러 인코딩에서 비슷하게 보인다.

| 인코딩 | `A`의 바이트 |
| --- | --- |
| ASCII | `41` |
| UTF-8 | `41` |
| UTF-16 BE | `00 41` |
| UTF-16 LE | `41 00` |
| UTF-32 BE | `00 00 00 41` |
| UTF-32 LE | `41 00 00 00` |

ASCII와 UTF-8에서는 `A`가 똑같이 `41` 한 바이트다. 그래서 처음 보면 "코드포인트 65가 곧 바이트 65인가?" 하고 착각하기 쉽다.

하지만 UTF-16으로 저장하면 `00 41` 또는 `41 00`처럼 두 바이트가 된다. 같은 글자, 같은 코드포인트인데 저장 바이트가 달라진다.

> 번호는 하나지만, 적는 방식은 여러 개다.

---

## 한글로 보면 바로 갈라진다

`A`는 너무 쉬운 예시라 층이 잘 안 갈라져 보인다. 한글 `가`를 보면 차이가 바로 드러난다.

| 글자 | 코드포인트 | UTF-8 바이트 | UTF-16 BE 바이트 |
| --- | --- | --- | --- |
| `A` | `U+0041` | `41` | `00 41` |
| `가` | `U+AC00` | `EA B0 80` | `AC 00` |

`가`의 유니코드 번호는 `U+AC00`이다. 그런데 UTF-8로 저장하면 `EA B0 80`이라는 3바이트가 된다.

즉 `AC 00`이라는 번호 느낌 그대로 저장되는 방식도 있고, `EA B0 80`처럼 UTF-8 규칙에 따라 쪼개져 저장되는 방식도 있다.

---

## JSON의 `\u0041`은 또 다른 층이다

JSON에서는 글자를 직접 넣을 수도 있고, `\u` 이스케이프로 적을 수도 있다.

```json
"A"
```

UTF-8 파일에 위 문자열이 저장되면 바이트는 이렇게 된다.

```text
22 41 22
```

`"`가 `22`, `A`가 `41`, 다시 `"`가 `22`다.

그런데 JSON에서는 같은 `A`를 이렇게 쓸 수도 있다.

```json
"\u0041"
```

이건 사람이 보기엔 `A`를 뜻하지만, 파일에 저장되는 바이트는 글자 그대로 전부 ASCII다.

```text
22 5C 75 30 30 34 31 22
```

풀어 쓰면 `"`, `\`, `u`, `0`, `0`, `4`, `1`, `"`가 저장된 것이다.

> `\u0041`은 UTF-8 바이트가 아니라, JSON 문자열 안에서 "유니코드 코드포인트 U+0041을 뜻한다"고 적는 표기다.

## Claude Code surrogate 버그와 연결

관련 노트: [[claude-code-prohan-surrogate-brick-bug]]

그 사건의 `\uD83A`도 이 JSON 이스케이프 층에서 봐야 한다.

파일에 진짜 깨진 UTF-8 바이트가 들어간 것이 아니라, JSON 문자열 안에 `\uD83A`라는 표기가 들어갔다. 문제는 `D83A`가 UTF-16의 high surrogate 범위라는 점이다.

surrogate는 이모지처럼 큰 코드포인트를 UTF-16에서 두 조각으로 표현할 때 쓴다.

- high surrogate: 앞조각
- low surrogate: 뒷조각

high surrogate는 반드시 low surrogate와 짝을 이뤄야 한다. 그런데 `\uD83A`만 있고 뒤에 low surrogate가 없으면 완성된 글자가 아니다.

그래서 JSON 파서 입장에서는 이런 상태가 된다.

> 문자열 안에 글자로 해석할 수 없는 반쪽짜리 유니코드 조각이 있다.

결과적으로 API는 request body를 유효한 JSON으로 받아들이지 못하고 `no low surrogate` 에러를 낸다.

## 백엔드 관점에서 기억하기

외부에서 들어온 문자열을 저장하거나 다시 전송할 때는 세 층을 구분해야 한다.

| 층 | 질문 | 예시 |
| --- | --- | --- |
| 코드포인트 | 이 글자의 번호가 뭔가? | `A = U+0041` |
| 인코딩 | 그 번호를 어떤 바이트로 저장할까? | UTF-8 `41`, UTF-16 BE `00 41` |
| 포맷 이스케이프 | JSON 안에서 어떻게 표기할까? | `"A"` 또는 `"\u0041"` |

장애가 났을 때도 이 셋을 섞으면 디버깅이 꼬인다.

- 글자 번호가 이상한가?
- 바이트 인코딩이 잘못됐나?
- JSON 이스케이프 표기가 깨졌나?

### 세 질문은 각각 무엇을 의심하는가

#### 1. 글자 번호가 이상한가?

이건 코드포인트 층 문제다.

정상적인 글자는 유니코드에서 하나의 번호를 가진다.

```text
냐 = U+B0D0
옹 = U+C639
A = U+0041
```

그런데 문자열 안에 독립된 글자로 볼 수 없는 번호가 들어오면 문제가 된다. 대표적으로 `\uD83A` 같은 값은 그 자체로 완성된 글자가 아니라 UTF-16 surrogate의 앞조각이다.

`D83A`는 high surrogate라서 뒤에 low surrogate가 있어야 완성된다. 혼자 있으면 문자열 안에 "글자"가 아니라 반쪽짜리 유니코드 조각이 들어온 상태가 된다.

> 원인: 애초에 문자열 안에 유효한 글자가 아니라, 반쪽짜리 유니코드 조각이 들어왔다.

#### 2. 바이트 인코딩이 잘못됐나?

이건 저장된 바이트를 잘못 읽은 문제다.

예를 들어 `냐옹`을 UTF-8로 저장하면 바이트는 이렇게 된다.

```text
EB 83 90 EC 98 B9
```

그런데 이 바이트를 UTF-8이 아니라 EUC-KR이나 CP949 같은 다른 규칙으로 읽으면 이상한 글자로 보일 수 있다.

> 원인: 바이트 자체는 있는데, "이 바이트를 어떤 인코딩으로 해석할지"를 틀렸다.

이게 흔히 말하는 글자 깨짐, 즉 `mojibake`다. 백엔드에서는 DB, 파일, HTTP 응답, 터미널의 charset이 서로 다를 때 자주 나온다.

#### 3. JSON 이스케이프 표기가 깨졌나?

이건 JSON 문자열 표현 방식 문제다.

JSON에서는 글자를 직접 넣을 수도 있고, `\u` 이스케이프로 넣을 수도 있다.

```json
"냐옹"
```

```json
"\uB0D0\uC639"
```

둘 다 의미상 `냐옹`이다.

그런데 이스케이프가 이상하면 JSON 파서가 문자열을 만들지 못한다.

```json
"\uB0D"
```

`\u` 뒤에는 16진수 4자리가 와야 하는데 3자리만 있으므로 문법적으로 깨진 JSON이다.

반면 아래는 더 미묘하다.

```json
"\uD83A"
```

`\u` 뒤에 4자리가 왔으니 표기 모양은 맞다. 하지만 `D83A`가 high surrogate라서 뒤에 low surrogate가 있어야 한다. 혼자 있으면 엄격한 JSON 파서는 유효한 문자열로 받아들이지 못한다.

> 원인: JSON 안에서 글자를 표현하는 `\uXXXX` 표기가 불완전하거나, surrogate pair가 맞지 않는다.

### 세 질문 정리

| 질문 | 층 | 원인 |
| --- | --- | --- |
| 글자 번호가 이상한가? | 유니코드/코드포인트 | 유효한 글자가 아닌 번호나 반쪽 surrogate가 문자열에 들어옴 |
| 바이트 인코딩이 잘못됐나? | 인코딩 | UTF-8 바이트를 CP949처럼 잘못 해석함 |
| JSON 이스케이프 표기가 깨졌나? | JSON 포맷 | `\uXXXX` 문법이 틀리거나 surrogate pair가 안 맞음 |

Claude Code surrogate 사건은 2번보다는 3번과 1번이 겹친 문제다.

파일에 깨진 UTF-8 바이트가 들어간 것이 아니라, JSON 안에 `\uD83A`라는 이스케이프가 있었고, 그 값이 의미상 짝 없는 high surrogate라서 문자열로 완성되지 못했다.

## 복습 답변 채점 및 피드백

> [!tip] 실제 공부 피드백
>
> **총점: 35/60점 (약 58점)**
>
> 코드포인트와 인코딩이 서로 다른 층이라는 핵심은 잡았다. 지금은 `U+0041`, `0x41`, 실제 바이트 `41`처럼 같은 숫자가 다른 문맥에서 보이는 부분과, JSON 원문이 파싱되기 전후로 어떻게 달라지는지를 더 구분하면 된다.
>
> ### 1. `A = 65`에서 65는 무엇인가?
>
> **채점: 9/10 — 거의 정답**
>
> `65`는 `A`에 붙은 코드포인트 번호의 10진수 표현이라는 답이 맞다. 유니코드 표기로는 `U+0041`이고, `0x41`은 같은 숫자 65를 16진수로 적은 것이다.
>
> 다만 `0x41`이라는 표기 자체가 곧 바이트인 것은 아니다. 숫자 65를 UTF-8이나 ASCII 규칙으로 저장한 결과가 **한 바이트 `41`**인 것이다.
>
> `65`, `0x41`, `U+0041`은 문맥과 표기법은 다르지만 숫자값은 같다. 그 숫자를 실제로 몇 바이트에 어떻게 적을지는 인코딩이 정한다.
>
> ### 2. 같은 `A`가 UTF-8과 UTF-16에서 왜 다르게 저장되는가?
>
> **채점: 4/10 — 문제 지점을 정확히 발견했지만 답은 아직 미완성**
>
> `A`도 서로 다르게 저장된다.
>
> - UTF-8: `41` — 1바이트
> - UTF-16 BE: `00 41` — 2바이트
> - UTF-16 LE: `41 00` — 2바이트
>
> 같은 코드포인트 `U+0041`을 각 인코딩이 자기 규칙에 따라 바이트로 적기 때문이다.
>
> `가`의 코드포인트 `U+AC00`도 먼저는 그냥 **숫자 하나**다. UTF-16에서는 BMP 범위의 코드포인트를 16비트 한 칸에 거의 그대로 담을 수 있어서, UTF-16 BE로 직렬화하면 `AC 00`이 된다.
>
> UTF-8은 다른 형식의 칸을 사용한다. `가`처럼 큰 번호에는 다음 3바이트 틀을 쓴다.
>
> ```text
> 1110xxxx 10xxxxxx 10xxxxxx
> ```
>
> `AC00`의 비트를 이 틀의 `x` 자리에 나눠 넣으면 다음 결과가 나온다.
>
> ```text
> EA B0 80
> ```
>
> 여기서 “쪼갠다”는 것은 글자 `가`를 여러 글자로 나눈다는 뜻이 아니다. **코드포인트라는 숫자의 비트를 UTF-8의 여러 바이트 칸에 나눠 담는다**는 뜻이다.
>
> 같은 주문번호를 종이 송장과 QR 코드에 서로 다른 규칙으로 적는 것과 비슷하다. 번호는 같고 표현 형식만 다르다.
>
> ### 3. JSON의 `"\u0041"`은 파일에 무엇으로 저장되는가?
>
> **채점: 3/10 — JSON 원문과 파싱 결과를 섞었다**
>
> JSON 파일 원문에 `"\u0041"`이라고 적혀 있다면 실제 바이트는 다음과 같다.
>
> ```text
> 22 5C 75 30 30 34 31 22
> ```
>
> 각각 `"`, `\`, `u`, `0`, `0`, `4`, `1`, `"`의 ASCII/UTF-8 바이트다.
>
> JSON 파서가 이 원문을 읽은 **뒤의 문자열 값**은 `A`가 된다. 그 `A`를 다시 UTF-8로 저장하면 `41` 한 바이트가 된다.
>
> ```text
> 파싱 전 JSON 원문: "\u0041"
> 파싱 후 문자열 값: A
> ```
>
> 네가 답한 `A`와 `0x41`은 파싱 후 결과 쪽에 해당한다.
>
> ### 4. `\uD83A`가 혼자 있으면 왜 안 되는가?
>
> **채점: 8/10 — 핵심 정답**
>
> high surrogate는 뒤의 low surrogate와 짝을 이뤄야 하므로 혼자 있으면 완성된 유니코드 글자가 아니라는 설명이 맞다.
>
> 다만 한글의 `ㄱ`에 비유하면 조금 다르다. `ㄱ`은 혼자서도 유효한 코드포인트와 문자지만, high surrogate 하나는 독립된 유니코드 문자로 인정되지 않는다.
>
> `ㄱ`보다는 UTF-16로 적은 이모지의 “앞쪽 절반만 도착한 상태”라고 기억하는 편이 정확하다.
>
> ### 5. 코드포인트, 인코딩, JSON 이스케이프는 어떤 층인가?
>
> **채점: 7/10 — 코드포인트와 인코딩은 이해했고 JSON 층이 빠졌다**
>
> 네 설명대로 코드포인트는 글자에 붙인 추상적인 번호이고, 인코딩은 그 번호를 실제 바이트로 나타내는 규칙이다.
>
> `A`의 코드포인트는 `41`이라고만 하기보다 **`U+0041` 또는 10진수 65**라고 말하면 문맥이 명확하다. UTF-8 결과 바이트도 우연히 `41`이라서 둘을 쉽게 섞기 때문이다.
>
> JSON 이스케이프는 그보다 위의 포맷 표현 층이다. JSON 문서 안에서 문자열을 `"A"`로 직접 적을지, `"\u0041"`로 적을지 정한다.
>
> ```text
> 코드포인트: 글자의 번호는 무엇인가?
> 인코딩: 그 번호를 어떤 바이트 배열로 저장할까?
> JSON 이스케이프: JSON 문서 안에서 그 글자를 어떤 문자 표기로 적을까?
> ```
>
> “숫자를 바이트로 만든다”는 말이 낯설다면 Java의 `int 65`도 떠올려볼 수 있다.
>
> - 32비트 정수로 저장: `00 00 00 41`
> - 문자열 `"65"`를 UTF-8로 저장: `36 35`
> - 문자 `"A"`를 UTF-8로 저장: `41`
>
> 추상적인 값이 같거나 관련되어 있어도 **어떤 자료형과 직렬화 규칙을 쓰느냐에 따라 바이트가 달라진다.**
>
> ### 6. 세 종류의 문제는 각각 왜 생기는가?
>
> **채점: 4/10 — 인코딩 문제의 방향은 맞지만 나머지 구분이 부족하다**
>
> 정확한 구분은 다음과 같다.
>
> | 문제 | 원인 |
> | --- | --- |
> | 글자 번호 문제 | 짝 없는 surrogate처럼 독립된 유니코드 글자가 될 수 없는 값이 들어옴 |
> | 바이트 인코딩 문제 | UTF-8로 만든 바이트를 CP949 등 다른 인코딩 규칙으로 **해석함** |
> | JSON 이스케이프 문제 | `\u` 뒤의 네 자리 문법이 틀리거나 surrogate pair의 짝이 맞지 않아 JSON 문자열 파싱에 실패함 |
>
> 네 답의 “UTF-8 바이트를 EUC 계열로 보면 이상한 문자가 된다”는 방향은 맞다. 다만 그 바이트를 다시 EUC-KR로 **인코딩한다**기보다, UTF-8 바이트를 EUC-KR이라고 잘못 알고 **디코딩한다**고 표현하는 것이 정확하다.
>
> 인코딩은 글자에서 바이트로 가는 방향이고, 디코딩은 바이트에서 글자로 돌아오는 방향이다.
>
> ### 최종 피드백
>
> 이번 답에서 가장 잘한 점은 모르는 부분을 얼버무리지 않고 정확히 걸린 지점을 적은 것이다. 특히 “애초에 숫자를 바이트로 만든다는 게 뭐지?”라는 질문이 핵심을 찔렀다.
>
> 지금은 다음 두 줄만 확실히 기억하면 된다.
>
> 1. 코드포인트는 숫자 하나이고, 인코딩은 그 숫자를 바이트 칸에 배치하는 규칙이다.
> 2. JSON의 `\u0041`은 JSON 원문 표기이고, 파싱하고 나서야 문자열 `A`가 된다.
>
## 한 줄 회고

- 헷갈렸던 점:
  - `A=65`는 저장 바이트가 아니라 유니코드 코드포인트다. JSON 원문의 `\u0041`에서 문자 `'0'`은 숫자값 `0`이 아니라 코드포인트 `U+0030`을 가진 글자이므로 UTF-8에서 `30` 바이트로 저장된다. JSON 원문 `"\u0041"`은 파싱된 뒤에야 문자열 값 `A`가 된다.
  - `냐 = U+B0D0`, `옹 = U+C639`의 `B0D0`, `C639`도 바이트 배열이 아니라 코드포인트 번호를 16진수로 적은 것이다. UTF-16 BE에서는 각각 `B0 D0`, `C6 39`로 거의 그대로 저장되지만, UTF-8에서는 길이와 연속 바이트를 표시하는 규칙에 따라 `EB 83 90`, `EC 98 B9`로 저장된다.
